01 Auth — where it breaks

A business flag is wired into an authorization check

The pattern, in 3 endpoints

# app/worklogs.py:28-41 — get_worklogs
employee_id = request.args.get('member_id')

if (not app_pkg._worklog_open
        and session.get('role') not in ELEVATED_ROLES
        and employee_id != session.get('member_id')):
    return jsonify({'error': 'Permission denied'}), 403
Defect A — the flag disables the check. _worklog_open means "the submission window is open". When it is True, the first term is False and the whole and chain short-circuits. Any Staff user reads any employee's worklogs by changing ?member_id=.
Defect B — type confusion. get_dashboard reads the param with type=int while the session holds an NVARCHAR string. int != str is always True — so the ownership term never matches even when the flag is off. worklogs.py:521-533

The fix — separate the concerns

# authorize unconditionally, normalize both sides
requested = str(request.args.get('member_id') or '').strip()
own       = str(session.get('member_id') or '').strip()

if session.get('role') not in ELEVATED_ROLES and requested != own:
    return jsonify({'error': 'Permission denied'}), 403

# _worklog_open governs WRITES only, further down

Third defect — same file High

update_worklog correctly verifies the existing row's owner at worklogs.py:387 — then takes member_id straight from the request body at :394 and uses it in the overlap query at :427-428, never validating it against that owner.

Effect: a Staff user edits their own row while reassigning it to someone else.

Root cause, all three: row-level authorization is hand-written per endpoint with no shared helper. Extract one — assert_can_read(employee_id) — and the class of bug disappears.

Why step 4 comes last. If Pending/Declined were rejected before the password check, response timing and wording would reveal which usernames exist. Checking after means a wrong password and a disabled account are indistinguishable. This is a deliberate anti-enumeration design and it is right.

Password storage Correct

scrypt : N=32768 , r=8 , p=1
via Werkzeug 3.1.8  (current)
  • Memory-hard — resists GPU/ASIC cracking
  • Per-password salt, one-way
  • Not MD5, not SHA1, not reversible encryption
  • No admin, and no DB reader, can recover a password

What is missing Medium

  • No minimum length
  • No complexity or passphrase rule
  • No breached-password check
  • No rotation or reuse history
Storage is excellent, but a 4-character password hashed with scrypt is still a 4-character password. The hash cannot compensate for the input.

Proxy-aware trust — done properly

Behind a proxy, request.host_url is always the local socket and never matches the browser's Origin. The CSRF hook resolves this with four layers:

  • X-Forwarded-Host — set by ngrok / tailscale serve
  • NGROK_DOMAIN — explicit trust from env
  • TAILSCALE_DOMAIN — explicit tailnet trust
  • request.host_url — plain LAN / localhost

Cookie Secure also auto-flips on when either domain is configured — so the cookie is not silently dropped over HTTPS.

The tunnel's own key is committed Critical

install-service.bat:23SECRET_KEY — a dictionary word
install-service.bat:24live ngrok authtoken
install-service.bat:25reserved ngrok domain
Impact of the authtoken: a third party can bind the same reserved domain and MITM every user — the URL your team has bookmarked would point at them.

Impact of SECRET_KEY: forge a session cookie asserting any user_id and role. Login throttling, lockouts, and password strength are all bypassed — the login endpoint is never touched.
Confirmed negative finding: .env is correctly ignored (.gitignore:160) and has never been committed — verified against full git history. The leak is the .bat defaults, not the env file.

06+ Frontend — the amplifier

The esc() trap

One helper, three call sites, two wrong contexts. This is the most likely source of the next incident.

// static/app/worklogs.js:473-477
function esc(s) {
    const d = document.createElement('div');
    d.textContent = s;
    return d.innerHTML;   // text-node serialization
}
Serializing a text node escapes only & < > and U+00A0. It escapes neither " nor '.

That makes esc() safe in exactly one context — and quietly unsafe in the two places it is most often reached for.

_psEsc() in projects-summary.js is the quote-safe version. Consolidate on it in core.js and delete the duplicate.

08 Remediation

Ordered backlog

Sequence matters — items 1–3 make every other control meaningful.

Now Secrets

  • Rotate SECRET_KEY; blank the .bat default
  • Revoke + reissue the ngrok token
  • Change/remove the seeded admin; drop the INSERT from init_db.sql
Rotating SECRET_KEY invalidates every session — everyone re-logs in. That is intended. Values remain in git history; treat them as burned.

Next Authorization & XSS

  • Remove _worklog_open from all 3 read checks
  • Normalize EmployeeID to str().strip() on both sides
  • Validate member_id in update_worklog against the row owner
  • Fix 3 XSS sinks; consolidate on a quote-safe escaper
  • Extract one shared assert_can_read() helper

Then Hardening

  • Add security headers — CSP first
  • Replace raw exception responses with generic text
  • Rate-limit /api/employee-lookup
  • Restrict ?inline=1 to image/PDF
  • Add a password policy (12+ chars)
  • Align storage paths; re-apply ACLs to the real drive

Pre-commit checklist

  • git diff --cached reviewed for keys/tokens/connection strings
  • All new SQL parameterized; dynamic identifiers whitelisted
  • Row-ownership check present, independent of any feature flag
  • EmployeeID normalized on both sides
  • Context-correct escaper used in the frontend
  • No raw exception text returned to clients

Two structural lessons

1 · Authorization needs one implementation. Three near-identical hand-written checks produced three different bugs. A single helper would have produced zero.

2 · Escaping is context-dependent, not value-dependent. esc() is not "the safe function" — it is safe in text nodes and unsafe everywhere else. Name helpers after their context.
